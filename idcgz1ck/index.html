Linux 通过 Firewalld 服务限制 IP 和端口

发表于2026-11-16|更新于2026-11-22|Linux 系统安全加固
|字数总计:4.2k|阅读时长:16分钟|阅读量:

零、先明确目标：你要限制的是哪一层

「限制 IP 和端口」这句话在 firewalld 里对应三种完全不同的需求，写法也不一样。先对号入座，能少走一半弯路：

需求 说人话 用什么实现
只让某些 IP 访问某个端口 白名单，如只允许跳板机连 SSH rich rule（富规则）或 ipset
所有端口对某些 IP 全开/全封 整机黑白名单 zone 的 source + target
限制某个端口对所有人开放 只开 80/443，其他一律关 --add-port / --add-service，不在规则里写 IP

firewalld 的核心概念只有四个，记住这四层就够用了：

  • zone（区域）：一套规则的容器，按「信任级别」划分。public 是默认区，trusted 是全放行，drop 是全丢弃。
  • service（服务）：端口 + 协议的命名封装，http = 80/tcp，省得记端口。
  • port（端口）：直接写 8080/tcp，支持范围 8000-8100/udp。
  • rich rule（富规则）：唯一能把「来源 IP」和「端口」绑在一条规则里的语法，也是本文重点。

还有一个必须刻在脑子里的区分：

runtime（运行时） 配置立刻生效， firewalld 重载/重启/机器重启就没了；permanent（永久） 配置写进 /etc/firewalld/，要 firewall-cmd --reload 才生效。
调规则的正确姿势是：先在 runtime 里试，确认没把自己锁在外面，再 --runtime-to-permanent 或加 --permanent 重写一遍。

2. 留好退路

改防火墙是少数「一个回车就把自己踢下线」的操作。三条保命建议：

  • 用云厂商的 VNC/串口控制台或物理机的 IPMI 开着第二个会话，ssh 断了还能救。

3.5 场景四：用 priority 控制先后顺序

富规则支持 priority（范围 -32768 到 32767，数值越小越先执行）。官方定义：

  • 负数优先级：在 firewalld 其他基础规则之前执行；
  • 0（默认）：按动作分链，日志 → 拒绝 → 放行；
  • 正数优先级：在其他基础规则之后执行。

priority 最常见的用途是让黑名单优先于普通放行规则。比如：zone 里放行了 http，但要把某个恶意 IP 彻底拉黑——默认优先级下 accept 可能先命中，拉黑就失效了。给它一个负优先级：

这样黑名单先生效，恶意 IP 的连接在到达 http 放行规则前就被丢弃并记日志。

记住富规则是首条匹配即终止：一旦被 drop 命中，后面的 accept 根本没机会执行。所以别写「先全封、再开小口」这种反向逻辑。白名单场景一律写成「逐条放行需要的，其余靠 zone target 兜底拒绝」。

四、IP 很多时用 ipset，别写几百条富规则

当白名单/黑名单超过十几个 IP，富规则会变得又长又难维护。firewalld 原生支持 ipset，一条规则引用一个集合：

动态封禁（配合 fail2ban 或自己的脚本）时，用不带 --permanent 的 --ipset 操作即可立即生效、重启自动消失；要持久化再加 --permanent。

ipset 的几个限制：

  • 集合类型要和规则 family 对上：hash:ip/hash:net 配 ipv4，IPv6 用 hash:ip6/hash:net6。
  • 一个集合被富规则引用时，不能直接删除集合，要先删引用它的富规则。
  • 条目很多时（上万级）注意内核 hash 表的内存占用。

五、临时规则与 --timeout：给自己留个自动撤销的保险

六、用 zone 做整机级的信任分级

富规则适合「IP + 端口」的精细控制，整机级信任用 zone 的 source 更简洁：

匹配逻辑（从具体到宽泛，第一个匹配生效）：

  1. 来源 IP 已绑定到某个 zone → 用那个 zone；
  2. 否则按入站网卡绑定的 zone；
  3. 都没有 → 用默认 zone（firewall-cmd --get-default-zone）。

七、Docker 场景：为什么你的规则「明明对了却不生效」

这是 firewalld 最经典的坑。Docker 启动时会自己往 iptables 写规则，docker run -p 发布的端口走 FORWARD 链 → DOCKER 链，在你的 zone INPUT 规则之前就被处理了。结果是：你在 public 区用富规则限制 8080，容器端口却依然对全网开放。

三种解决思路，按推荐度排：

方案 A：端口只绑本地，交给反向代理（最推荐）

宿主机上再用 Nginx 监听公网端口做反代，访问控制回到 firewalld 手里。云上还可以直接把安全组当作第一道门。

方案 B：在 DOCKER-USER 链写规则

Docker 专门留了 DOCKER-USER 链给用户，Docker 自身不会覆盖它。用 firewalld 的 direct 接口写入以便持久化：

两个细节：

  • 端口映射会做 DNAT：host 8443 → container 443 的场景，规则里要匹配容器端口 443，不是宿主机的 8443。
  • firewalld 重载会冲掉 Docker 的链：firewall-cmd --reload 之后如果容器访问异常，重启 Docker 服务让它重建链。

方案 C：跟踪最新变化

Docker Engine 29 起提供实验性的 --firewall-backend=nftables，规则不再走 iptables，原有的 DOCKER-USER 链需要迁移。生产环境用 Docker 26/27 + iptables 后端最省心；升级前务必先确认防火墙策略的迁移路径。

顺带提醒：云主机上还有安全组 / 网络 ACL 这一层，它和主机防火墙是「与」的关系——安全组没放行，主机上配得再对也连不上；反过来也一样。排查时两层都要看。

十、完整示例：一台 Web 服务器的加固顺序

需求：对外只开 80/443；SSH 只允许跳板机 203.0.113.10；数据库 3306 只允许内网 10.20.0.0/16；其余全部拒绝。

最后从另一台机器分别测试：跳板机 SSH 应通、其他 IP SSH 应超时、公网 80/443 应通、公网 3306 应超时。本机自测不作数——本机回环流量不一定经过你以为的那套规则。

小结

  1. 端口开关用 --add-port / --add-service；IP + 端口必须用富规则；大量 IP 用 ipset。
  2. 富规则第一条匹配即生效，写 source 必须带 family，改 priority 前先想清楚链的顺序；与其「先封后开」，不如「只放行 + 默认拒绝」。
  3. runtime 试、permanent 固化、--reload 生效；远程改规则永远留 --timeout 或控制台退路。
  4. Docker 的端口不走 zone INPUT，要么绑 127.0.0.1 交给反代，要么写 DOCKER-USER 链。
  5. 云上还要叠加安全组这一层，两边是「与」关系。

把 --list-all 的输出和富规则字符串存进配置管理（Ansible/脚本），比每次手敲命令可靠得多——防火墙规则最怕的不是写错，而是「当时写对了，后来没人记得为什么」。
